# 主动式智能第一阶段：故障、软件适配与上游协作

2026-09-29 提案，2026-09-30 实施中。以下保留设计依据；当前实现与验收以文末记录为准。未对外提交。

## 产品目标与范围

主动发现手机上影响用户的错误和软件适配缺口，先参考仓库维护的兼容性知识库，解释实际影响，让 Agent 接手调查、准备修复并验证；将适合共享的成果反馈给正确的上游，并追踪到发行和用户设备。用户在本轮进一步明确：仓库应维护各类软件的兼容性指南/知识库，作为判断依据。

第一阶段包含三条入口：故障发现、软件适配检查、上游问题与修复跟进。共用一套问题记录和证据链。日程、个人习惯推断、通用长期助理暂不进入本阶段。

用户看到的是“什么受影响、Agent 能做什么、目前做到哪一步”。普通用户无需管理源码仓库或参与维护者讨论。

## 核心交互：何时告知、如何呈现、择机处理

用户进一步明确：核心是推送时机、呈现方式，以及用户能择机处理；统一呈现在 Agent 助理软件的“建议”栏目。以下为第一版交互提案，尚未实施。

采用“持久事项卡 + 按需通知 + 明确的稍后安排”。发现时先保存事项，是否发通知单独判断。通知负责引导，事项卡负责长期承接；清除通知不删除问题、不表示已解决、不代表同意执行。

### 何时提醒

先判断不处理会有什么影响、是否正在影响用户、现在是否存在有用的下一步，再根据可观察的使用状态选择时机。严重程度与可打扰程度分别记录；不要由模型猜测用户已经空闲。

| 场景 | 时机与呈现 | 下一步 |
|---|---|---|
| 用户刚执行的操作失败，如启动退出、保存失败 | 错误已发生、界面可呈现时给一条简短通知；已有等价错误提示时合并，避免再弹一层 | 查看影响、检查原因或使用已知恢复办法 |
| 关键能力持续不可用、继续操作可能无法保存数据 | 及时明确提示影响；仍遵守系统通知和勿扰设置，不自行抢占全屏或绕过勿扰 | 可执行的恢复/保护措施，或说明暂时无恢复方案 |
| 软件可用，但发现适配或性能改善机会 | 先入待处理；在使用相关软件告一段落、返回桌面且无已知通话/录屏/全屏任务等时，静默提示一次；识别不了合适时机则保留在列表 | 查看改善建议、让 Agent 检查/准备方案 |
| 同一问题重复发生 | 更新原卡次数和影响；只有影响升级或出现新办法时才重新提醒 | 继续原事项，不新建多条提醒 |
| Agent 已完成调查，需要用户选择或中断应用才能应用修复 | 完成准备后提醒一次，明确需要占用多久、关闭什么；无法估计时说明未知 | 现在应用、择机处理 |
| 上游评审、合入等进展 | 更新事项详情，普通用户不逐条推送；已有适用于本机且验证过的修复时再通知 | 安排应用更新 |

安装完成或每次解锁都不自动成为推送机会。第一版不推断复杂生活习惯，使用可核验事件和用户指定时间/条件。默认普通优化不响铃、不震动、不语音播报；通知权限、勿扰和用户类别偏好决定最终呈现。

### 呈现位置与卡片内容

- Agent 助理的“建议”栏目是统一承接位置，故障、优化机会和可用修复均以建议卡呈现。“待处理”是建议的状态，不另设同级入口；此前关于侧边栏新增“待处理”入口的提案由此替代。
- 栏目优先展示当前影响使用或需要用户决定的事项，其次是可择机处理的优化。已选“稍后”的卡片仍在栏目内，显示约定时间或条件；委托后原卡显示 Agent 的处理进度，完成后进入历史。第一版不强制拆成多个独立页面。
- 系统通知点击后直接打开对应事项，带上现有证据与进度；不要求用户重新描述问题，不自动启动修改。
- 同一事项在聊天、通知、列表中共用记录。用户正在查看该事项时原位更新；后台准备不自动展开语音浮层、助理屏或切换用户当前对话。
- 卡片展示：发生了什么、对使用的影响、判断依据摘要、下一步、执行代价、处理状态。“检查原因”“准备方案”“应用修复”分别命名，不用一个含糊的“优化”混合三种授权。
- 操作控制保持简洁：一个当前主要动作和“稍后”；详情内提供“不再提醒这个问题”。只有下一步是应用修复时才显示对应的重启/关闭应用要求，不把工程过程全部塞进通知。
- Android 与 Plasma 的通知展示应按当前可见环境路由，同一事项只有一份主动提醒。桥接接口、后台可达性与锁屏动作需要另外核验；锁屏仅显示必要摘要，需认证的操作留到解锁后。

### “稍后”必须有明确语义

| 用户操作 | 系统承诺 |
|---|---|
| 收起或划掉通知 | 通知消失，事项仍在待处理；不因划掉而马上再弹 |
| 保留待处理 | 不设提醒时间，用户可以从固定入口随时继续 |
| 指定时间提醒，如今晚或明天 | 保存具体当地时间；到时先复核问题是否仍存在，再按通知设置提醒；不自动执行修复 |
| 条件满足时提醒，如应用关闭后 | 明确显示条件，条件满足后提醒一次；条件从未满足则保留“等待条件”，不误报已安排完成 |
| 不再提醒这个问题 | 保留记录并停止本问题的普通主动提醒；用户可恢复；不同版本/独立新问题重新判断，不能仅换措辞绕过选择 |

默认“稍后”可先保留待处理，并在轻量面板中提供具体时间和条件选项，不强迫用户现在安排日程。“今晚”等预设必须在界面显示实际时间；错过时间后最多补发一次仍有效的提醒，不集中补发历史通知。

“提醒我处理”和“满足条件自动处理”必须分开。第一版提供前者；用户已明确授权自动执行的任务才可使用后者，并显示具体动作、等待条件、取消入口和授权范围。充电或应用退出本身不构成修改软件的许可。

### 通知与处理的生命周期

每张卡另存提醒状态：尚未提示、已提示、已查看、留待处理、已约定提醒、已静音；这与本地故障状态、上游状态独立。至少记录问题 ID/版本、通知 ID、上次提示原因/时间、再次提示条件、用户选择和提醒有效期。

第一版采用保守的频率规则：每个问题首次合适时提示一次；普通优化的主动提醒合并为摘要，每天至多一次（建议初始值，待体验验证）；用户明确约定的提醒另行兑现。同一次使用过程不连续弹出多项优化。发生新影响或已有可应用的新方案才允许重新评估提醒，不能因日志重复或 Agent 换了一种说法重新打扰。

发送提醒和执行动作之前，都重新检查问题是否仍存在、软件版本是否变化、方案是否过期、用户是否已自行解决。旧通知打开最新事项；过期的应用操作失效并说明原因。更新解决的问题移入已完成并撤销待发提醒。

用户选择让 Agent 检查后，任务在其授权范围内继续；关闭卡片或离开应用不取消任务。暂停/取消由明确动作表达。需要用户参与时保留完整上下文进入“需要你处理”，用户几小时后回来仍能直接继续。通知不可用或被清空时，这条路径也必须成立。

### 一条完整体验

用户播放视频时出现持续掉帧 → 系统保存证据并匹配知识库 → 用户退出播放、返回桌面后收到静默提示“刚才播放不够流畅，可以检查是否存在适配问题” → 用户选择明天提醒 → 明天再次确认问题未因升级解决后提醒 → 用户点“检查原因” → Agent 调查并准备方案 → 卡片显示“方案已准备好，应用时需要关闭播放器” → 用户选“播放器关闭后提醒我” → 提醒后用户应用 → 验证结果，成功则归档，失败则回退并保留后续入口。

## 仓库兼容性知识库是共同依据

处理链固定为：事件 → 本机环境与实际影响 → 查询兼容性知识库 → 判断记录是否适用 → 复核/调查 → 准备和验证处理方案 → 回写知识库 → 按需反馈上游。

知识库用于发现、解释、修复和验证各阶段，不能等 Agent 自行尝试之后才查。已验证方案无需每台手机重新研究；仍要核对本机前提和结果。没有记录表示未知，不能显示为“不兼容”；标记“已验证”也不表示这次手机状态一定相同。

### 内容组织

建议新增仓库目录 `compatibility/`，本轮只确定职责，尚未创建目录或实现解析器：

- `apps/`：应用身份、安装来源、版本，以及界面渲染/编解码/输入等各项能力，关联共享组件问题。
- `components/`：Mesa、Qt Multimedia、PipeWire、portal 等共享组件的已知问题与修复，使多应用复用同一条知识。
- `policies/`：设备和工作负载下的已验证默认策略及适用限制，例如 Blender 的 CPU 渲染选择。
- `schema/`：条目格式与版本约束；供轻量匹配、发布校验和 Agent 读取。

结构化条目负责匹配条件、状态及引用，现有 `docs/` 继续保存调查推理和验收过程，`packages/` 继续保存真实补丁和构建配方。不要复制成三份独立维护的事实；指南可由条目和文档引用组成。设备原始日志、core、截图仍留在 `.work/` 或设备，不进公共知识条目。

每条知识至少记录：

| 字段 | 作用 |
|---|---|
| 稳定 ID、类型、摘要 | 关联问题、应用、共享组件和上游 |
| 软件身份与来源 | 区分发行版包、Flatpak/AppImage、Android 包等；未知来源不套用已知包结论 |
| 适用条件 | 软件/依赖/驱动版本，设备/GPU、固件、系统发布、会话/容器、功能与工作负载 |
| 现象和检测依据 | 已知症状、实际后端、支持的检测方法；不能仅凭关键词判定 |
| 结论状态 | 待核实、已复现、已验证方案、有意限制、已被新版本取代等 |
| 处理方案 | 配置、已有更新、共享层修复或补丁引用，副作用及回退；也可以明确“当前无方案” |
| 验收证据 | 基线、实测环境、前后结果、测试方法、日期；推测、离线测试和实机测试分别标明 |
| 上游关系 | 问题/MR/提交/修复版本，及本地补丁关联 |
| 维护信息 | 负责人、复核日期、替代条目、需重新验证的条件 |

版本判断遵循对应包管理器的规则；不能用字符串比较版本。未验证范围不自动外推，例如一个机型的 GPU 测试不能覆盖所有 Adreno，一项视频格式的测试不能覆盖全部硬件解码。

### 知识的使用和更新

1. 应用安装、升级或运行出现症状后，按实际身份匹配条目。匹配缺失条件则先补证据，不能直接执行修复。
2. 对已知且适用的问题，展示具体影响与已有方案；对有意限制保持现有策略；对未知问题让 Agent 接手调查。
3. 核对近期上游代码/修复状态，尤其在版本超出已验证范围或知识已过期时。记录冲突保留为待复核，不能由模型默默选一条。
4. 调查输出形成知识库变更候选，记录新发现、证据及适用边界。未经验证的推断可以留作研究记录，不进入“自动应用的已验证方案”。
5. 按仓库审阅和发布流程纳入知识库；同类设备随后复用该结论。上游合入、软件升级或新回归会触发条目复核、替代或退役。

知识库是一套指导判断的数据，不提供任意可执行命令入口。自动检查/修复只引用受控工具和有版本的修复方案，并继续检查授权与设备状态。同步新的知识不能自行扩大 Agent 权限。

手机持有随发布版本绑定的本地知识快照，断网时仍可匹配。后续可以独立更新知识数据，但须保留来源、版本、工具兼容约束与回退；不直接执行远端文档或 issue 中的指令。

第一批条目从已验证历史提炼：崩溃归并及诊断资源限制（61篇）、Qt Multimedia 音频问题（73篇）、Blender 渲染策略（90篇）。需逐条补齐精确环境，不把历史实机结果自动标成当前全机型兼容。

## 统一问题记录

每个问题分配稳定 ID，关联多次观测、调查任务、修复方案和上游记录。最低字段：

- 身份：设备/固件/系统发布，应用来源、版本与构建标识，相关共享组件版本。
- 发现：类别、首次/最近时间、出现次数、指纹、触发时所做的事。
- 判断：用户影响、严重程度、事实、原因假设、证据完整度；明确区分这几者。
- 归属：应用、发行版打包、Rungic 共享接口、驱动/分支或尚未定位。
- 处理：已知方案、适用条件、预期收益、测试与回退、授权范围、当前执行任务。
- 知识与外部关联：匹配的知识条目及版本、问题链接、PR/MR、上游提交、包含修复的版本、本地补丁与本机安装版本。
- 呈现：是否已提醒、用户忽略/稍后/委托、再次提醒条件。

采用两条独立状态轴，避免“已提交 PR”被显示成“手机已修好”：

1. 本地：发现 → 待核实 → 已确认 → 方案准备 → 验证 → 可应用 → 已应用待验收 → 已解决；另有证据不足、已缓解、暂缓、不适用、验证失败/回退。
2. 上游：未评估 → 已知问题/待反馈 → 材料就绪 → 已提交 → 评审中 → 已合入 → 已发行 → 本机已包含；另有不适合上游、被拒绝或已撤回。

进程退出、命令成功和 PR 合并都不能单独作为本地问题解决的判据。重启后保留记录和委托；重复事件归并，修复后再出现则重新打开并保留原证据。

## 入口一：哪些错误需要用户注意

第一批信号：新的崩溃签名、关键服务失败或重启循环、应用启动失败、Android 低内存终止与容器内 OOM、存储不足、包安装失败与版本漂移。Android 证据通过现有宿主桥的受控接口接入，覆盖不到的明确标未知。

先由轻量规则归并，再由 Agent 按需分析。日志中的 error 单词只作线索，不直接生成通知。SIGKILL、无响应和没有 core 均不能单独推出崩溃原因。

| 影响 | 产品行为 |
|---|---|
| 当前操作失败、重要功能持续不可用或数据保存受影响 | 及时说明影响和下一步；同一故障持续更新一张卡 |
| 反复退出、性能明显退化、存在已验证解决方案 | 在适当时机提醒，并提供“让 Agent 检查/处理” |
| 单次可恢复问题、已知无害日志或原因不明且尚无影响证据 | 记入问题列表；证据或影响变化后再决定提醒 |

建议文案：“这个应用今天意外退出了 3 次。我已保留诊断信息，可以继续检查原因。”尚未归因时不写“驱动有问题”。

调查本身须有限额。61篇记录过手机上符号化耗尽内存、导致 Android 终止 VPN 与桌面的事故：复用现有受限采集和构建机符号化路径；不要在用户手机后台自动编译或运行重负载探针。

## 入口二：发现适配与优化机会

安装/升级后建立应用清单并匹配已知规则；在首次实际使用相应功能、发生异常或用户主动要求时补充运行证据。包管理器事件的具体接入及 Flatpak 等来源覆盖留待实现时核验。

能力按功能分别记录：界面渲染、视频解码、视频编码、计算、音频、输入与窗口适配。GPU 驱动可用不能证明应用正在使用它，界面 GPU 渲染也不能证明视频解码已加速。

每项能力记录“应用应使用什么 → 当前实际路径 → 证据 → 不匹配原因/未知 → 可行方案”。状态至少包括：已验证正常、已验证可优化、待核实、当前不支持、有意采用的兼容策略。

硬件加速的调查顺序：

1. 核对具体任务、格式和硬件/驱动支持范围，以及用户或系统的明确选择。
2. 优先读取应用诊断与实际后端证据，结合日志、掉帧和资源数据；CPU 高占用不能单独证明缺少加速。
3. 定位是配置、沙箱运行时、软件包构建、标准接口、驱动还是应用自身的问题。
4. 查已有适配及上游修复，准备能撤销的候选方案。
5. 用同一工作负载核对正确性、流畅度、内存及可测的能耗；没有实測收益时只标候选。

90篇的 Blender 是必须纳入的反例：隔离测试没有复现所称的 Vulkan 故障，CPU 渲染是用户选择的内存与稳定性策略。检测到 CPU 渲染不能提示“修复为 GPU”，更不能覆盖现有选择。

用户提示分两种：

- 已有证据和方案：“检测到视频播放使用软件解码，有一项适用于此版本的适配可供验证。”提供“让 Agent 验证 / 稍后”。
- 只有线索：“播放过程中持续掉帧，原因还未确定。”提供“让 Agent 检查”，不承诺能够加速。

处理优先级遵循项目约定：正确配置和现成包 → 共享标准接口/后端 → 必要的应用补丁。共享层修复需交叉验证多个独立应用；一次应用测试通过不扩展为整个系统已兼容。

## Agent 的执行与权限

自动完成授权范围内的轻量本地检查、已知问题匹配、证据归并和方案准备。用户委托后，Agent 在该范围内持续调查和验证，避免反复询问同一授权。

已有且验证过的修复可以在用户启用的自动处理范围内应用。新补丁、驱动替换和会话重启等动作必须有明确的适用条件、回退和部署授权；先做出可审阅结果。桌面工作区只提供交互隔离，不是测试共享库或驱动的安全隔离；后者使用构建/测试环境，最后才进入受控实机验收。

后台调查默认不抢用户焦点、不关闭用户应用。遵循现有“不自动后台编译”的约定。版本变化后重新检查方案适用性；限制重试、资源消耗与自动修改次数。日志和上游内容只是证据，不能成为扩大权限的指令。

## 入口三：上游协作

反馈由 Rungic 维护端统一整理，同一根因只保留一条对外跟踪主线。第一版可以只做本地账本、仓库知识库和人工维护端流程，无需先建设云端遥测；跨设备归并只使用用户允许共享的脱敏证据。知识库变更与上游 PR/MR 分别跟踪：已验证的本地经验可以先进入知识库，不等待上游接受代码。

1. **找到责任边界**：核对实际源码与版本，在去除本地补丁或最小复现中确认。发行版打包问题报发行版，KGSL 分支特有问题先核对分支维护者，通用上游缺陷报对应项目。
2. **查已有记录**：检索现有 issue、MR、提交和修复版本；已有修复时优先验证升级或回移，避免重复报告。
3. **准备材料**：最小复现、预期/实际行为、精确环境和版本、脱敏回溯、基线对照；有修复时补上最小补丁和回归测试。
4. **遵循项目规则提交**：维护上游注册表，包括来源/许可证、issue 和 PR/MR 入口、目标分支、贡献规则及查询日期、AI 使用要求、联系负责人。规则适用于报告、代码、提交说明及后续讨论，不能只检查第一次提交。
5. **持续跟进**：响应评审、更新测试、记录合入与发布状态；进入 Rungic 发布并在设备验收后，再标记本机解决。上游正式包含修复后，通过补丁队列移除重复补丁。

本地修复和对外协作分别推进：用户可以先得到经验证的本地修复，不必等待上游合并。73篇此前“不以提交上游作为减少补丁的手段”的限制，仍用于避免交付依赖评审周期；本轮新增的是持续反馈与合作机制。

71篇已有责任归属纠正案例：为微信的尺寸请求放宽 KWin 协议检查，不能因此认定 KWin 有缺陷并向它提交通用修复。保留兼容补丁与报告客户端问题是两件事。

### 当前核对到的上游要求（2026-09-29）

- [Mesa 提交规范](https://docs.mesa3d.org/submittingpatches.html)：使用 GitLab MR，提交者负责理解、测试、许可证和评审跟进。当前规则禁止自主工具自动提交或自主参与 issue/MR；并要求贡献者自己撰写对外文字，对适用的 AI 代码辅助作披露。因此面向 Mesa 的 Agent 输出只能作为内部调查和代码辅助材料，维护者按规则自行撰写并提交、沟通，不能只设计成“自动生成后点一下发送”。
- [Mesa 错误报告](https://docs.mesa3d.org/bugs.html)：按项目要求准备可复现、包含环境与诊断信息的报告。
- [DEP-3](https://dep-team.pages.debian.net/deps/dep3/)：沿用 `Origin`、`Bug`、`Forwarded` 等来源与反馈信息；结合现有 `X-Rungic-Status/Tests/Docs` 关联验证记录。
- KDE 的通用贡献页面本轮直接访问返回 403，搜索结果不足以完成完整规则核验；实际提交前读取目标仓库及现行规则，不能套用 Mesa 或推断 KDE 一律允许自动贡献。

core、完整日志、账户/路径/文档内容不默认上传。原始证据保存在设备或 `.work/`；对外使用最小脱敏复现，上传内容与目标在授权范围内可审阅。用户同意本机诊断不等于允许对外公开。

## 第一版交付与验收

第一版 UI 使用 Agent 助理的“建议”栏目与持久建议卡，按用户需要采取的动作及处理状态组织；故障/优化作为标签。系统通知点击后回到同一张建议卡。PR、补丁队列和详细日志在展开详情或维护端查看。

第一版闭环选择：

1. 一个已有崩溃签名：发现、归并、说明影响、接手调查、验证解决或给出证据不足结论。
2. 一个有明确功能证据的适配缺口：发现、定位到正确层、准备方案、对照验证、回退；暂不指定必须成功加速的应用。
3. 一个适合上游的问题：复现与去重、责任归属、贡献规则核对、材料准备、人工/授权发布流程及后续状态关联；实际对外提交需具体授权，本轮不提交。

验收覆盖：同一错误不重复轰炸；未知不冒充已确认；用户既定 CPU 策略不被误报；相似但不匹配的版本/机型不会误用知识条目；本地缓解不冒充根治；PR 合入不冒充本机更新；重启可恢复处理状态；失败可停止或回退；采集和调查不会显著干扰日常使用。

交互验收另外覆盖：用户忽略首次通知后仍能在“建议”栏目找到事项；划掉不等于解决或授权；稍后约定跨重启保留；错过提醒不连发；通话/全屏使用期间普通优化不打断；进入 Android 后提醒可达且不与 Plasma 重复；应用升级后旧方案不能执行；问题已解决会取消提醒；关闭卡片后已委托任务继续；缺少通知权限时仍可从“建议”栏目接续。

指标记录有效提醒率、误报与重复提醒、调查后定位比例、修复后同签名复发、优化前后实测变化，以及采集/调查的资源成本。上游看有效反馈与长期补丁减少，不以提交数量作为目标。

具体探针、通知阈值和上游连接器尚未选型。实现前继续核对源码与接口；生产新增组件按项目要求使用 C++ 等实现。此次文档不改变已部署能力、SSH 策略或现有应用偏好。


## 2026-09-30 实施：纵向卡片主屏

用户最终要求用建议卡片流作为 Plasma Mobile 主屏，上滑应用抽屉保持原功能。复用固定 Plasma Mobile 6.6.5 Folio 源码及现有补丁队列，新补丁 0015 替换主屏显示层，保留已有桌面布局数据、抽屉、快速设置与任务切换。主屏内手势用于纵向滚动，底部独立入口点击或上滑打开原应用抽屉。上游文件沿用 LGPL-2.0-or-later，新建议服务为 GPL-2.0-or-later。相比重写整个 shell，只改主屏承载与手势边界，继续复用成熟组件。

`plasma/suggestions/` 是 C++/Qt 服务、共享 QML 卡片与客户端；Agent 栏目和桌面读取同一个会话 D-Bus 账本。`compatibility/entries/` 保存精确版本范围和证据；政策条目不产生故障告警。打包携带引用文档与补丁，调查可先在本机读取。

当前探针：保留七天的崩溃签名及包版本、系统与用户 failed 服务、磁盘余量、dpkg audit、精确包版本的知识匹配。崩溃所属包已变更或移除时撤下旧卡。没有覆盖 Android LMK、逐应用 GPU/编解码实际使用、通话状态判断；不把 CPU 策略或安装成功当成适配结论。未知检测能力不显示为系统全部健康。

当前普通机会直接进入主屏，非紧急建议不会在应用使用期间弹出。明确预约的提醒、紧急存储问题和委托任务完成使用系统通知；可见建议页抑制重复通知。使用系统通知设置，不推断用户空闲。通知暂仅 Plasma，会话关闭期间不新增 Android 推送；错过提醒在恢复并刷新证据后兑现。

操作包括检查、查看原对话、稍后、明天 10 点、应用退出后（存在进程证据时）、忽略与恢复。调查结束保留待处理；仅探针复查不再符合条件才移入历史，不宣称根因已修好。应用修复要求具体计划、验证、回退，用户展开阅读并确认；“稍后”不执行。Agent 沿用既有运行权限，诊断的只读范围由任务指令约束，不是新增 OS 沙箱。

上游机制为本地脱敏材料、规则注册表及带链接的维护者状态记录；不自动公开日志、不伪造 PR。Mesa 按当前规则由人撰写公开文字并提交。上游状态与本机解决状态独立，尚未自动轮询远端评审。

离线验证使用 ARM64 Ubuntu/Qt 6.10.2，真实 C++ 服务与 QML、私有 D-Bus 和 40 张合成卡片；Agent 传输使用测试替身，不将它当作真实模型验收。模型覆盖持久化、去重、延后、静音、条件提醒、问题消失、损坏记录保留、上游合入与本机状态分离。实机证据追加在后续验收段。
