# Rungic 三段式镜像制作

交付目标：从锁定输入制作指定机型的完整包，清数据刷入后自行准备运行环境，以真实 loading 等待就绪，再允许配置账户并进入 Plasma。内核按机型/固件构建；用户空间按架构和后端需求复用；设备差异进入 spec 或适配器。

这是项目内 skill。命令和正文中的源码路径均相对仓库根目录；先定位根目录并读取 `AGENTS.md`。参考文件内链接按文件所在目录解析。源码、spec、补丁及 skill 随 Git；生成物、日志、备份和缓存仅放 `.work/`。

## 进入任务

1. 从用户请求确定范围：方案、新机型接入、单阶段构建、整包制作或授权的实机部署。沿用已给出的目标与授权；仅制作 skill/方案/候选包不授权刷写。刷写和清数据若已有明确授权，核验目标后继续，不重复确认。权限缺失时先完成可离线完成的工作，再说明具体待执行操作。
2. 先读 `docs/80-g100-image-installation-retrospective.md` 与 `docs/77-g100-three-ci-assessment.md`；涉及具体失败再读 79 篇相关段落。75/77 的计划与 79/80 的已实施状态要区分，最终以当前源码及对应 release 证据为准。
3. **新机型或固件变化**先读 [新机型接入](references/device-onboarding.md)。执行构建前读 [工具地图](references/tool-map.md)，涉及首启/刷机失败读 [首启与故障处理](references/first-boot.md)。
4. 适配前查固定版本的上游源码、同类方案、已知问题、许可证和实机兼容性，按 `AGENTS.md` 先确认各宿主代理。记录复用/修改的理由；不能只照搬 G100 配方。
5. 在 `.work/ci/runs/<run-id>/` 保存本次输入、阶段状态和证据。绑定源码 SHA（未提交修改另留补丁及摘要，不能只填 HEAD）、spec SHA、OEM SHA、内核配方、包版本/摘要和 release-id。未知硬要求阻止依赖它的阶段，独立工作可继续。

## 三段流程与放行条件

### CI1：自编 GKI 与设备启动镜像

- 由目标 spec 选择 ACK/Kleaf 提交、工具链、页大小、配置、补丁、boot 格式、OEM 模块和信任关系。修改过的上游继续用 `packages/<名称>/recipe.json` 和 DEP-3 补丁队列维护。
- 优先只增加 Rungic/LXC 必需能力。对照 OEM 模块核验 ABI/符号 CRC 和签名信任，记录可比较范围、缺失及未知项；相同 Android 版本、KMI 名称或 SoC 不能替代核验。
- 使用设备支持且已核验的候选启动方式验证 Android、OEM 模块、SELinux 和容器必需机制。临时启动不受支持时，按该设备的恢复方案选择测试路径，不能默认所有手机都有 `fastboot boot`。
- 产出候选内核/boot、来源与配置、ABI/信任报告、静态及实机能力证据。报告关联实际交付摘要；编译成功或旧内核探针不能授予候选兼容结论。

### CI2：RungicOS 用户空间镜像

- 锁定 ARM64 软件包、基础发行版、Rungic 版本和宿主桥协议，选用满足目标硬件的图形/媒体后端。rootfs 与 Android 共享 CI1 的内核。
- 按 runner 能力分工。当前工作站适合 GKI 交叉构建和镜像组装，Mac mini 适合定制 ARM64 包原生构建；更换 runner 时检查架构、工具、代理和容量，不将机器地址写成通用前提。
- 在干净 rootfs 中安装精确依赖。x86 上安装 ARM64 包可用 QEMU + 真 chroot；核验维护脚本。QEMU 执行 ARM64 程序和源码交叉编译是两种不同方式。
- 检查包锁、`dpkg --audit`、项目 venv 的 `pip check`、UID/权限/xattr、日志目录和文件系统。禁止依赖开发机已有包或把个人账户、密码、家目录备份打进镜像。
- 产出 rootfs、压缩种子、包锁、摘要与报告。根目录固定容量、图形包组合都要根据目标重新核对，不能把 G100 的 16 GiB/KGSL 当作普遍条件。

### CI3：设备发行包、部署与验收

- 只消费 CI1/CI2 已校验的产物和精确 OEM 输入。先核对 [工具地图](references/tool-map.md) 的设备假设；新增 spec 不代表现有刷写器已适配。
- 按 spec 逐包执行纯净化，区分物理移除和默认排除安装。AI 功能依据包依赖/角色核查，不凭名称一刀切；保留启动、电话、权限和必要输入入口。
- 组装 Android 分区、APK 与 JNI 库、宿主种子、rootfs、root 提供者和首启组件；核验容量、元数据/SELinux、AVB 方案、boot 格式和报告间摘要。载荷放入经验证的只读分区或安装介质，不复制设备加密的 userdata。
- 发行包包含单一入口、分区载荷、安装器、manifest/摘要、spec、报告、使用及恢复说明。模式切换由已验证的刷写计划驱动；不能默认所有设备需 fastbootd、固定槽 a 或相同分区集合。
- 离线验证包完整性后，在授权的目标上完整刷写并清数据。每条设备命令绑定端口/序列号；写前再次核对身份、解锁、槽位、容量/电量及恢复输入。输出真实阶段、流式日志和超时信息；失联或设备拒绝时停止写入，保留现场，重新识别后再制定恢复动作。
- 最终验收从**发行包本身的清数据安装**开始，覆盖 Android 启动、离线部署、loading、账户创建及实际 Plasma 显示。无需开发者手工拷贝、补装或修复 root 才能进入系统；普通 Android 引导和用户账户配置仍是正常交互。

## 首次进入的公共契约

遵循 [首启与故障处理](references/first-boot.md)：

`Android 初始化 → root 提供者就绪 → 校验/展开/配置 → 存储与挂载预检 → 发布 ready → account-prepare → 账户表单 → 桌面 loading → Plasma`

- 应用显示实际阶段。状态原子发布并关联本次 release；缺失、旧版、错误或截断状态不提前放行。root 控制入口独立校验完成标记。
- 等真实存储、挂载、容器与账户工具就绪；未知耗时用不定进度，等待有超时和可诊断错误。用户无需反复提交密码；重新打开入口可恢复观察安装状态。
- 修复落在公共准备入口，让账户配置、正常启动与重试复用。G100/Magisk 31 的一次首启重启是具体实现，不要求其他 root 提供者机械复制。

## 验收、交付与清理

阶段记录区分 `candidate → offline-verified → flashed → android-accepted → rungic-accepted → bundle-validated`；这是工作流契约，现有工具未必自动写出全部状态。每次提升状态注明 release、摘要和证据。

- 原机事实、候选内核探针、已有数据测试、受控 UI 测试、整包清数据验收和用户反馈分别记录。未知项不写通过，跳过项写明原因；旧候选报告不能挪给新包。
- 用户指定验收范围优先。本轮已排除的相机等测试不擅自重启；未来任务按其 spec/用户范围选择必需与可选项目，不能永久取消所有设备的硬件验收。
- 实机成功后保存可独立使用的完整发行包、恢复输入及报告，并回读摘要。完成归档立即按 run-id 清理本次构建暂存/缓存，核对本机及远端空间；保留正式产物、必要依赖快照和证据，不执行全局 prune。
- 失败先保留日志和必要现场，大型可重建暂存按明确保留期回收；构建中监控空间，低于预留量停止新重型阶段，不靠删除其他任务材料续跑。
- 汇报交付目录、release/spec/源码及产物摘要、实际验证范围、未决问题与清理结果。当前 skill 提供可复用的制作方法，不能将单机验证称为所有同型号设备可用。
